## 2026-10-02 — 残留清理：**分组目录**不再算残留（否则 `--apply` 会删掉活产物）

- **背景**（改名那轮在本机撞见的）：标签里带 `/` 的目标（工作区子目录里的仓库，如
  `~/dev/plugins/dsh-cold-backup` → 标签 `plugins/dsh-cold-backup`）在备份目录里是**嵌套**的：
  产物在 `<DEST>/repos/plugins/dsh-cold-backup`。而 `orphan_scan()` 只枚举 `$DEST/repos/*`
  的**直接**子目录 —— 于是 `repos/plugins` 被当成一个标签去比对，必然匹配不上任何已知标签，
  就被报成「残留」。
- **危害**：`--status` 把它列进 `orphans[]`，还附一句「清理：`--prune-orphans --apply`」；
  而 `--apply` 执行的是 `rm -rf "$DEST/$rel"` —— **照着工具自己给的提示做，就会把
  `repos/plugins` 下面所有插件的活备份删掉**（本机实测：6.6 MB、六个插件）。
  同一形态还误报了 `repos/dsh`（它下面是活目标 `dsh/notify-v2` 的产物目录）。
- **选项**：A 只把「是已知目标产物路径前缀」的目录跳过；B 改成递归枚举 + 前缀判据；
  C 不改代码，只在文档里写「有嵌套标签的工作区别用 `--apply`」。
- **结论**：**B**。A 会把嵌套的**真残留**（例如 `repos/plugins/dsh-dev-backup` —— 插件改名后
  正该清掉的那份）永久藏起来；C 等于把工具的 bug 降级成用户的注意事项，而那条提示每天都弹。
  实现：`orphan_scan()` 改为 `find "$DEST/<kind>" -mindepth 1 -type d` 递归枚举，
  候选目录只要「等于某个已知目标」或「是某个已知目标产物路径的前缀」就跳过。
- **保守之处（有意的）**：若「`plugins` 自己也是目标」且它消失了、而 `plugins/foo` 还在，
  `repos/plugins` 顶层的陈旧产物不会被列为残留 —— **宁可漏报，也不误删**，这是备份工具的底线。
- **验证**：自测新增第 26 节（11 项断言）；变异测试（把前缀判据拿掉）稳定红 6 项，
  其中一项就是「⑤ 活产物被误删」—— 说明这条护栏真的拦得住这个 bug。
- **本机私有脚本同步修掉**（同一份逻辑）：真机 `--prune-orphans` 的 dry-run 从
  「7 个待删」变成「7 个待删」——**但成分变了**：两个会误删活产物的假阳性消失，
  两个此前看不见的嵌套真残留（`repos/plugins/dsh-archived-sessions-manager`、
  `repos/plugins/dsh-dev-backup`）浮出来。

## 2026-10-02 — 改名：`dev-backup` → `cold-backup`、`dsh-dev-backup` → `dsh-cold-backup`

- **背景**：这两个名字里的 `dev` 既不准确也不自解释 —— 「dev-backup」读起来像「开发用的备份」，
  而它实际做的是**冷备**（离线快照 + 可还原，区别于实时同步）。作者拍板：名字里要出现「冷备」。
- **选项**：A 只改包名与命令名，路径 / 环境变量 / JSON schema 等契约标识继续用 `dev-backup`
  （改动最小，但从此两套名字并存 —— 正是要避免的那种不一致）；B 全部改，干净断代；
  C 新名为主 + 兼容旧名（读旧路径、接受旧环境变量）。
- **结论**：**B**。依据是「几乎还没有存量用户」这个窗口不会一直在：两个包 2026-09-30 才发布，
  已知用户只有作者本人，此时断代成本最低；拖到有用户之后再改，就得永久养 C 那层兼容。
  换名清单：包名、可执行文件 `bin/cold-backup`、`COLD_BACKUP_*` 环境变量、默认目录
  `~/Library/Logs/cold-backup`（Linux `~/.local/state/cold-backup`）、配置文件
  `~/.config/cold-backup/config`、JSON schema `cold-backup.status/1`、归属标记
  `.cold-backup-owner`、crontab 标记 `# >>> cold-backup >>>`、launchd label 模板
  `com.cold-backup.daily`、临时文件名前缀。插件侧同步：包名 / 入口 id / 路由
  `/dsh-cold-backup/status` / 默认状态文件路径 / schema 前缀。
- **代价 / 后续**：
  ① **npm 不支持给包改名** —— 旧包 `dev-backup`、`dsh-dev-backup` 只能 deprecate（附指向新名的说明），
     不能重定向；GitHub 仓库可以改名，旧 URL 自动 301。
  ② 已存在的备份目录里是旧标记 `.dev-backup-owner`：在新版本眼里等于**没有标记**，
     按 `unowned`（「大概是自己的」）处理，行为与旧版一致、不会误删；要恢复标记语义需手工
     `mv`（`compatibility.md` §7 给了命令）。
  ③ **旧定时任务不会被接管**：crontab 标记与 launchd label 都换了，不手工卸载就会每天跑两次。
  ④ 本机私有链路（`_shared/bin/backup-dev.sh` + macOS 面板）跟着改 `LOG_DIR` 默认值；
     私有脚本自己的 `DEV_BACKUP_*` 变量名属于私有仓库内部接口，**不在**本次改名范围内 ——
     公开 CLI 与私有脚本是两个程序，各自的名字各自管。
  ⑤ 版本号**不跳**：`cold-backup` 首发就是 `1.0.2`、`dsh-cold-backup` 首发就是 `1.1.1`，
     与旧包同版本同内容（只差名字），让装了旧包的人能一对一地迁过来。

## 2026-10-02 — 同秒并列：轮转不许删「刚写出的产物」，校验/演练按 HEAD 挑产物

- **背景**：产物名是 `<标签>-<UTC 秒>-<提交前12位>`，**只有秒精度**。同一秒内为两个提交各备一次时，
  两份产物的秒相同、只剩 sha 后缀可比 —— 「按名排序」在这个并列下退化成按 sha 随机排。
  CI 上因此出现过三次失败（第 7、11、14 节），且 macOS 绿、ubuntu 红、重跑仍红：
  ubuntu runner 够快，自测里连续「提交 + 备份」真的会落在同一秒。
- **两个是真问题（产品侧）**：
  ① `prune()` 按名保留最新 KEEP 份，**并列时可能把本轮刚写出的那份删掉** —— 而调用方刚刚才报「备份成功」；
  ② `--restore-drill` / `--verify` 用「按名取最新」挑产物做深校验，并列时可能抓到**旧提交**那份，
     于是把一次完好的备份报成「不一致」（假失败）。
- **选项**：A 把产物名的时间戳加精度（改成毫秒/加序号）；B 不改名，把「刚写出的那份」与
  「对应 HEAD 的那份」当作显式判据；C 只在文档里写「别在同一秒提交两次」。
- **结论**：**B**。A 会改产物命名契约（`compatibility.md` 里写了时间戳格式与「按名取最新」的前提，
  消费方与既有产物都会受影响），代价远大于收益；C 是让人替工具记规矩。
  具体：`prune()` 增加第 3 个参数（本次刚写的产物，永不删）；新增 `head_bundle_of()`
  供 `--verify` / `--restore-drill` 优先挑 HEAD 那一份（HEAD 还没备上时才退回最新那份）。
- **顺带得到的东西**：`test/frozen-clock.sh` —— 把产物时间戳钉成同一个值再跑整套自测，
  **把「同一秒」从时序巧合变成常态**，CI 两个平台各跑一遍。它是这个 bug 类的确定性回归护栏：
  修复前稳定红 2~7 项（每次抽签不同），修复后连续多轮全绿。
- **代价 / 后续**：并列仍然存在（文件名本身无法区分），所以 `compatibility.md` 明确写了
  「消费方不要依赖并列时的顺序」；真要彻底消除得改名（上面的 A），留给下一个大版本权衡。

## 2026-10-02 — 两个防护：`DEST` 不许在工作区里、`--program` 必须可执行

- **背景**（都是 1.0.0 发布后实测出来的）：
  ① 把 `DEST` 指到工作区里面（`ROOT=~/dev`、`DEST=~/dev/backup`）时，「非 git 顶层目录打快照」
  会把**上一轮的产物**打进去 —— 实测 3 轮快照 3194 → 6945 → 14110 字节，**逐轮翻倍**，
  备份会自我繁殖到撑爆磁盘；`DEST == ROOT` 更极端（把整棵工作区打一遍）。
  ② `schedule install --program /不存在的路径` 会照常写好 plist 并加载，任务每天静默失败 ——
  而「定时任务到底跑了没有」正是这个工具存在的理由。
- **选项**：A 只在文档里写清楚；B 运行时直接拒绝 DEST 落在 ROOT 里 + 装任务时警告 program 不可执行；
  C 给两者都加 `--force` 逃生口。
- **结论**：**B**，**不加 C**。① 是没有任何正当用法的配置（真要把产物放在工作区里，应当把那个目录
  加进 `EXCLUDES` 或关掉 `SNAPSHOTS`，而不是让工具猜），所以按错误处理并退出 1；
  ② 允许「先装任务、稍后再构建程序」的合理场景，所以只警告不失败。
  判定用**规范化后的路径前缀**（`canon_path`：存在的走 `pwd -P`，不存在的用「规范化父目录 + 名字」），
  这样 `~/dev` 与 `/Users/x/dev`、`/tmp` 与 `/private/tmp` 这类写法不会被判成不同路径。
- **代价 / 后续**：极端情况（比如把 DEST 挂在 ROOT 下的一个挂载点）会被误拒，那时只能把产品目录
  移出去 —— 判断是：这种布局比「备份自我繁殖」罕见得多，值得用一次误拒换掉一个静默的磁盘炸点。
  两条防护都有自测（第 25 节，9 项断言）。

## 2026-10-02 — 公开版不动既有契约：泛化只在「配置层」与「可移植层」

- **背景**：`backup-dev.sh` 在本机已经跑了很久，产物布局、JSON、退出码、`last-ok` /
  `last-failure` 被三个消费方依赖：macOS 面板（Swift，`Engine.swift` 解析 JSON 与 launchd 状态）、
  已发 npm 的 DSH 插件 `dsh-dev-backup`（前缀匹配 schema、只认 `verdict ∈ {ok,bad}`）、
  以及全局 git 钩子（只依赖退出码）。同时它带着一堆本机假设：OneDrive 目标、`~/dev` 根、
  个人配置白名单（`~/.claude`、`~/.codex`、`~/.dsh`）、写死的通知标题与 FDA 提示文案。
- **选项**：A 重写一个干净的通用版本（接口自由，但三个消费方全要改，且会丢掉两年的踩坑经验）；
  B 保留全部接口，只在下面加「配置层 + 可移植层」，本机专有值搬到配置文件；
  C 只把本机版打个包发出去（把个人路径写进公共包）。
- **结论**：**B**。所有子命令、环境变量、退出码、JSON schema、产物布局、`last-ok` /
  `last-failure` 格式**逐字节保持不变**；新增的是：配置文件（KEY=VALUE）、`--config/--root/
  --dest/--logdir`、`--init`、`--version`、`schedule`，以及 `file_size/file_mtime/sha256_*/
  stamp_to_epoch` 等可移植封装。**验证方式**：把本机私有仓库那套 677 行、122 条断言的自测
  直接指向新 CLI 跑 —— 除了两条依赖 `_shared/app` 目录布局的面板本地化断言，其余全绿。
- **代价 / 后续**：字符串常量（如 schema）仍在代码里硬编码，只是加了 lint 保证它和文档一致；
  将来若要「多份配置 / 多后端」，得再开一层。

## 2026-10-02 — 归属标记 `.dev-backup-owner`：宁可不备，也不动别人的产物

- **背景**：孤儿清理（`--prune-orphans --apply`）与轮转删除的判据是「当前工作区的目标集合」。
  标签是**工作区内的相对路径**（`plugins/foo`），两台机器或两个工作区指向同一个同步目录时
  会撞名：A 机器会把 B 机器的产物当「残留」删掉。这是**数据丢失**，不是清理。
- **选项**：A 不管，文档里写「一个 DEST 只给一个工作区用」；B 给每个目标目录写一份归属标记，
  归属不符时拒绝写入 / 拒绝删除；C 在目标目录下按工作区 ID 分层（`<DEST>/<id>/repos/…`）。
- **结论**：**B**。标记文件 `.dev-backup-owner`，内容 = 工作区 ID（默认主机名 + 工作区根路径的
  指纹，可用 `WORKSPACE_ID` 固定）。三类处理：`ours` 正常；`unowned`（没有标记的老产物）
  按「大概是自己的」处理，保持与旧版本一致的行为；`foreign` 则 `--status` 只报告、
  `--prune-orphans --apply` 绝不删、备份时拒绝写入并让整轮非零退出。
- **代价 / 后续**：多了一个每个目标一份的小文件，要在兼容性文档里说明「它不是产物」。
  C 更彻底但要改产物布局（`repos/<标签>` 外面再套一层），会让所有现存产物与文档失效，不做。

## 2026-10-02 — 只读子命令严格只读；`die` 不再污染 `last-failure`

- **背景**：老版本**任何**模式都会 `mkdir -p $LOGDIR $TMP` 并可能轮转日志；`need_git` 失败时
  走的 `die` 还会写 `last-failure`。于是「看一眼状态」既产生副作用，又可能把「本机没装 git」
  写成「上次备份失败」，污染下一轮判定的输入。
- **选项**：A 维持现状，只在文档里说明有副作用；B `--status` / `--version` 不建目录不写文件，
  且 `last-failure` 只在 `backup` / `daily` 模式下写。
- **结论**：**B**。`last-failure` 的语义是「上次**备份**失败了」，只有会备份的模式才配写它。
- **代价 / 后续**：`--status` 在日志目录不可写时不再报错（它本来也不需要写）。这是行为变更，
  但方向是「更少的隐式副作用」，对外契约（退出码、JSON）不变。

## 2026-10-02 — 人读文案保持中文，机器可读 token 保持英文

- **背景**：这个工具要公开给陌生人用，那么「人类可读的输出该用哪种语言」就成了必须决定的事。
- **选项**：A 全英文；B 全中文；C 人读中文 + 机器可读全英文；D 做 i18n 开关。
- **结论**：**C**。理由：① 既有的三个消费方都不解析人读文本（面板原样贴、插件只读 JSON），
  唯一例外是面板靠子串「完全磁盘访问权限」点亮一个按钮 —— 那是中文契约，改了要同步改 Swift；
  ② reason code、upload token、JSON 字段名**本来就是英文**，机器那一侧不受影响；
  ③ 作者的另一半工具链（README、决策记录）也是中文优先，混着来反而更难维护。
- **代价 / 后续**：英文用户看 `--status` 的人读文本会吃力（JSON 与 `--help` 里的关键词是英文）。
  真要 i18n，正确做法是加 `LANG=en` 并**只**翻译人读文案，机器可读部分不许动。

## 2026-10-02 — 不引入 `warn` 档：`verdict` 永远只有 `ok` / `bad`

- **背景**：「上传中」这类中间态看起来很适合做黄灯。但已发布的 DSH 插件只接受
  `verdict ∈ {ok,bad}`，其它值会让它**整份丢弃**你的文档并静默退回旧逻辑 ——
  表面还能用，实际已经不看你的判定了。
- **选项**：A 加 `warn` 并同步发插件新版；B 不加，中间态用 `reasons[].code` 表达。
- **结论**：**B**。黄灯由消费方按 reason code 自己决定怎么显示；JSON 契约保持二值。
- **代价 / 后续**：想加必须先改消费方（面板 + 插件发版），并且要能接受「老版本会静默降级」。

## 2026-10-02 — 保留 bash 3.2 下限，可移植性只做「兼容层」

- **背景**：macOS 系统自带 bash 3.2，而 macOS 的 launchd / git 钩子通常就用它；另一侧，
  GNU 工具链上 `stat -f%z`、`date -j -f`、`shasum` 会**静默**给出空值或错值
  （bytes 变 0、产物时间退回 mtime），不是报错。
- **选项**：A 要求 bash 5 并统一用 GNU 语义；B 保留 3.2 下限，把 BSD/GNU 差异收口到几个函数；
  C 只支持 macOS，不做兼容层。
- **结论**：**B**。`file_size` / `file_mtime` / `sha256_file` / `sha256_stdin` / `stamp_to_epoch`
  几个封装，其余代码不感知平台。bash 4 专有语法（`declare -A`、`mapfile`、`${x^^}`、`local -n`）
  由 `test/lint.sh` 拦死，并在 CI 的 macOS 分支上用 `/bin/bash`（3.2）再跑一遍端到端。
- **代价 / 后续**：作者手上没有 Linux 机器，Linux 目前只有 CI 覆盖；要宣称「支持某发行版」得先
  在那上面手工跑一次 `--verify` 与 `--restore-drill`。

## 2026-10-02 — 分发：npm 为主，`install.sh` 兜底；不做 systemd timer

- **背景**：工具本身是纯 bash，不需要 Node；但「让人装得上、能升版本」需要一条正经渠道。
- **选项**：A 只发 GitHub（clone + install.sh）；B npm 包里放同一个脚本（`bin` 指向它）+
  `install.sh` 给没有 Node 的人；C 连 systemd timer 一起做。
- **结论**：**B**。npm 提供版本号、`npx` 免安装试用、以及和作者其它包一致的发布链路
  （trusted publishing + provenance）。**C 不做**：cron 已经覆盖 Linux，systemd 用户的正确
  姿势是自己写一个 unit 调 `--daily`（退出码语义一样），不必进这个包。
- **代价 / 后续**：`package.json` 里 `os` 限 `darwin` / `linux`（Windows 上没有 bash 语义）。

## 2026-10-02 — 公开版的默认值必须是「通用值」，个人约定搬到配置文件

- **背景**：老版本会三级探测 OneDrive 目录、默认收 `~/.claude`、`~/.codex`、`~/.dsh` 的白名单
  配置、通知标题写死 `~/dev OneDrive 备份`。这些在公共包里既没用又吓人（会去 tar 陌生人的 home）。
- **选项**：A 保留探测，作为「开箱即用」的便利；B 默认值全部通用化：`DEST` 必填、
  `CONFIGS=off`、不做任何云盘探测；本机约定由本机自己的配置文件提供。
- **结论**：**B**。`--status` 在未配置时输出合法的「未配置」文档（`reasons: [unconfigured]`，
  退出 2），而不是猜一个目录。
- **代价 / 后续**：陌生人第一次用必须改两行配置（`ROOT`、`DEST`）。换来的是「不会在你不知情的
  情况下把东西写到别处」。
